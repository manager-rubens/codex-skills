# Professional PRD Outline

Use this structure when generating the final Product Requirements Document. Adapt labels to the user's language.

## 1. Title and Metadata

- Product or feature name
- PRD version
- Date
- Owner or stakeholder, if known
- Status: Draft, Review, Approved, or Build-ready

## 2. Executive Summary

Describe the product, target audience, core value proposition, and intended business or user outcome in 1 to 3 paragraphs.

## 3. Problem Statement

Explain the user or business problem, why it matters, and what currently happens without the product.

## 4. Goals and Non-Goals

List measurable goals and explicit non-goals. Non-goals prevent accidental scope creep.

## 5. Target Users and Personas

Define primary and secondary roles, their context, needs, motivations, and pain points.

## 6. Core Use Cases and User Journeys

Describe the main workflows from trigger to successful outcome. Include alternate and failure paths when relevant.

## 7. Scope

Separate:

- MVP scope
- Post-MVP enhancements
- Out of scope

## 8. Functional Requirements

Use a prioritized table:

| ID | Requirement | Priority | User Value | Acceptance Criteria |
| --- | --- | --- | --- | --- |

Priorities can use Must, Should, Could, Won't or P0, P1, P2.

## 9. User Stories

Use the format:

`As a [user/role], I want [capability], so that [benefit].`

Add acceptance criteria for the most important stories.

## 10. UX and Information Architecture

Describe screens, navigation, empty states, errors, onboarding, and key interaction patterns. Avoid prescribing visual design unless the user gave brand or UI constraints.

## 11. Data, Integrations, and Permissions

List core entities, data sources, integrations, roles, permissions, privacy considerations, and export/reporting needs.

## 12. Non-Functional Requirements

Cover performance, reliability, accessibility, security, compliance, localization, device support, and observability when relevant.

## 13. Success Metrics

Define activation, engagement, retention, conversion, task success, operational, or revenue metrics. Include analytics events if useful.

## 14. Risks, Assumptions, and Dependencies

Call out product, technical, market, data, legal, operational, and adoption risks. State assumptions plainly.

## 15. Release Plan

Suggest a pragmatic MVP delivery sequence: discovery/prototype, build, beta, launch, post-launch learning.

## 16. Open Questions

List decisions that remain unresolved and identify which should be answered before development starts.

## 17. Implementation Handoff

When the user may continue into development, include a concise build prompt or engineering handoff summarizing the MVP scope, core screens, data model, and acceptance criteria.
